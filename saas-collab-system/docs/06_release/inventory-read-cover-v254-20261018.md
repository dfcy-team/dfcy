# V2.44.254 库存工作台读取优化候选

基线：阿里云 V2.44.253，`5f4652bf2c2f8e265b0d574be194926497cd2290`。

库存工作台仓库汇总在读取最新库存身份时超时。生产只读诊断中，仓库汇总 SQL 在 8,006ms 被诊断会话保护中止；这不是系统的全局请求上限。MySQL 8.4.11 执行计划显示按租户扫描约 320,400 条历史行，现有索引不能覆盖 `source_run_id` 条件。

候选仅将 `idx_inv_latest_lookup` 替换为 `idx_inv_latest_cover`：原字段、排序方向完整保留，末尾追加 `source_run`。不修改查询逻辑、接口响应、租户和权限筛选、跨同步批次最新身份选择、风险与虚拟商品过滤、每日趋势、明细队列或超时配置。

曾验证拆开排名、同步批次子查询、MAX 时间分组等方案；单独应用均未通过生产诊断保护，已撤销所有视图代码改动。

- 70 项库存工作台、库存分析、仓库报表权限相关测试通过。
- 39 项 commerce 模型、事实数据契约、库存 SKU 关联测试通过；合计 109 项。
- Django check、makemigrations --check 通过；SQLite 0008 回退至 0007 再前进至 0008，索引名称状态核对通过。
- 独立 MySQL 8.4.11、128MiB buffer pool、100 万条合成历史，其中 60 万条符合源批次条件、1 万个库存身份：窗口查询约 5,190ms → 1,420ms。EXPLAIN ANALYZE 确认使用 covering index；结果 count 和 hash 一致。

原始证据保存在工作区 `审计产物/V254库存读取优化_20261018/`。合成数据库不含生产明细，专用容器测试结束后删除。

## 发布与回退

候选包含 commerce.0008 数据库索引迁移。MySQL 使用单条 `ALTER TABLE ... ADD INDEX ... DROP INDEX ... ALGORITHM=INPLACE, LOCK=NONE`，不重写业务记录。迁移仅临时设置自身连接的 `lock_wait_timeout=15`，成功或失败后恢复原值；仍可能短暂等待元数据锁。不得通过移除 LOCK=NONE 强行降级为锁表操作。

发布前检查实际版本漂移、索引现状、磁盘临时空间和长事务；本次只读预检确认生产为 InnoDB Dynamic、16KiB 页、128MiB buffer pool，旧索引字段方向与模型一致。实际迁移由发布通道受控执行，不在本地候选验证中执行生产 DDL。

部署后使用现有运营账号验证库存工作台、完整 SQL 耗时、仓库合计、14 个实际观察日趋势、风险/虚拟商品过滤和明细穿透；区分空数据与读取失败。检查同步任务写入耗时及延迟，出现实质退化则回退。首页月销售优化留待后续独立版本。

回退必须保持数据库索引与代码迁移状态一致：若 commerce.0008 仍为该应用最新迁移，可受控回退至 0007 恢复旧索引；存在后续迁移时先评估依赖，采用前进修复，不直接跨版本回退。逆向在线 DDL及测试库回退已验证。
