# 阿里云硅谷 VPC 应用层与数据库迁移实施方案（最终版）

版本：V1.0  
日期：2026-08-11  
目标地域：阿里云美国西部 1（硅谷），Region ID `us-west-1`  
适用阶段：受控试点、云上平行验证及后续正式切换

## 1. 最终结论

本项目采用阿里云美国西部 1（硅谷）VPC，首期保持现有“两台主机分层”拓扑，通过全新 ECS 重新部署应用、通过 DTS 迁移 MySQL 数据，不对应用 VM 做整机搬迁。

最终起步规格如下：

| 节点 | 操作系统 | 计算规格 | 系统盘 | 数据盘 | 结论 |
|---|---|---:|---:|---:|---|
| 应用 ECS | Ubuntu Server 22.04 LTS | 2 vCPU / 4 GB | 80 GB ESSD | 无 | 可用于受控试点和早期低负载生产 |
| 数据库 ECS | Ubuntu Server 22.04 LTS | 2 vCPU / 8 GB | 60 GB ESSD | 100 GB ESSD | 当前数据库占用不超过约 40 GB 时可采用 |

若数据库 ECS 已经购买为 40 GB 系统盘，无需重建，但 MySQL 数据、Binlog、临时目录和备份必须迁出系统盘。若尚未购买，建议直接选择 60 GB 系统盘。

现在适合建设云上平行环境、进行 DTS 同步和完整迁移演练；正式域名和写流量仅在云上环境连续稳定、验收及回退演练全部通过后切换。

## 2. 当前基线与迁移原则

### 2.1 当前部署基线

- 应用层运行 Django、Gunicorn、Celery Worker、Celery Beat、Redis 和前端 Nginx。
- 数据库层运行原生 MySQL 8.4.x。
- 当前应用 VM 实测为 2 vCPU、约 4 GB 内存；空闲时应用容器合计约占 0.5 GB，系统盘已用约 16 GB。
- 项目当前属于受控试点基线，不应把首次上云、正式投产和真实高风险自动化接入安排在同一窗口。

### 2.2 迁移原则

1. 应用重新部署，数据库增量迁移。
2. 云上环境与现有 VM 并行存在，先验证后切换。
3. 使用固定 Git SHA 和固定 OCI 镜像摘要，目标 ECS 不执行构建。
4. 数据库只通过私网访问，3306 不开放公网。
5. 迁移前必须有可恢复备份，切换前必须完成一次回退演练。
6. 在目标数据库开始承接正式写入前保留简单回退能力；开始新库写入后，不得无同步方案直接切回旧库。

## 3. 目标架构

```text
用户 / 受控办公网络
        |
    HTTPS 443
        |
  ALB 或应用 ECS EIP
        |
应用 ECS（Ubuntu 22.04）
Nginx + Django + Celery + Redis
        |
  VPC 私网 TCP 3306
        |
数据库 ECS（Ubuntu 22.04）
MySQL 8.4 + 独立 ESSD 数据盘
        |
 OSS / 云备份 / 自动快照
```

首期可将两台 ECS 放在同一可用区以降低数据库访问时延。进入较高可用性生产阶段后，应演进为跨可用区多应用 ECS + ALB，并优先评估 RDS 高可用版替代单节点自建 MySQL。

## 4. VPC 与安全规划

### 4.1 地址规划

| 对象 | 建议配置 |
|---|---|
| 地域 | 美国西部 1（硅谷），`us-west-1` |
| VPC | `10.20.0.0/16` |
| 应用交换机 | `10.20.10.0/24` |
| 数据库交换机 | `10.20.20.0/24` |
| 运维 / VPN 交换机 | `10.20.30.0/24` |

创建前必须确认上述网段不与现有 VMware、办公网络、VPN 客户端地址池冲突。

### 4.2 安全组

**应用安全组 `sg-saas-app`**

- 443：允许正式用户或 ALB 访问。
- 80：仅用于跳转 HTTPS，非必要时不开放。
- 22：只允许堡垒机、VPN 或固定运维公网 IP。
- 8000 等后端容器端口：只绑定本机，不允许公网访问。

**数据库安全组 `sg-saas-db`**

- 3306：只允许应用安全组来源。
- 迁移期间按 DTS 预检查结果临时加入必要来源，迁移结束后移除。
- 22：只允许堡垒机、VPN 或固定运维入口。
- 数据库 ECS 不配置 EIP，不允许 `0.0.0.0/0` 访问 3306。

### 4.3 身份与密钥

- 阿里云主账号开启 MFA，仅用于账户级管理。
- 日常运维使用 RAM 子账号和最小权限策略。
- ECS 禁止 root 远程登录，关闭 SSH 密码登录，使用独立 Ed25519 密钥。
- 应用、数据库、DTS、备份账号相互独立。
- `.env`、数据库密码、TLS 私钥和备份密钥不得进入 Git、镜像或普通日志。

## 5. ECS 与存储配置

### 5.1 应用 ECS

| 项目 | 最终配置 |
|---|---|
| 操作系统 | Ubuntu Server 22.04 LTS 最新点版本 |
| CPU / 内存 | 2 vCPU / 4 GB |
| 系统盘 | 80 GB ESSD |
| 交换空间 | 2-4 GB，仅作突发保护 |
| 运行组件 | Docker Engine、Compose、Nginx、Django、Celery、Redis |
| Gunicorn | 起步 2 workers |
| Celery | 起步并发 1-2，根据队列积压调整 |

必须为 Docker 日志配置轮转；镜像拉取、容器日志和临时文件不得无上限占用系统盘。

### 5.2 数据库 ECS

| 项目 | 最终配置 |
|---|---|
| 操作系统 | Ubuntu Server 22.04 LTS 最新点版本 |
| CPU / 内存 | 2 vCPU / 8 GB |
| 系统盘 | 推荐 60 GB ESSD；已购 40 GB 可保留 |
| 数据盘 | 100 GB ESSD，建议 PL1 或满足等效数据库 IOPS 的类型 |
| 数据库 | Oracle MySQL 8.4 LTS，与源库小版本保持一致或先验证兼容性 |
| Swap | 可配置约 4 GB，应告警且不能长期发生交换 |

建议目录：

```text
/data/mysql       MySQL 数据目录
/data/mysql-bin   Binlog
/data/mysql-tmp   临时目录
/data/backup      短期本机备份缓存
```

本机备份不能作为唯一备份，必须同步至 OSS、云备份或其他独立存储。

### 5.3 100 GB 数据盘适用条件

容量估算公式：

```text
所需容量 = 当前数据库占用 x 2 + 7 天 Binlog + 迁移临时空间 + 未来 6 个月增长量
```

| 当前数据库占用 | 100 GB 数据盘判断 |
|---:|---|
| 小于 20 GB | 充足 |
| 20-40 GB | 可用，需设置容量告警 |
| 40-50 GB | 偏紧，建议 200 GB |
| 超过 50 GB | 直接选择 200 GB 或更大 |

数据库盘日常使用率目标不超过 60%，70% 告警，80% 必须扩容或清理。

## 6. 操作系统与软件基线

Ubuntu 22.04 可用于本项目。部署前应完成：

- 安装全部批准的安全更新并重启。
- 确认无 `/run/reboot-required`。
- 启用时间同步，系统统一使用 UTC，业务界面按需求转换时区。
- 固定 Docker、Compose 和 MySQL 的安装来源及主版本。
- 使用 MySQL 官方 APT 仓库安装 8.4 LTS，不依赖 Ubuntu 默认 MySQL 版本。
- 配置 UFW 与阿里云安全组形成双层限制。
- 配置日志轮转、云监控、操作审计和主机告警。
- 规划在 Ubuntu 22.04 标准支持结束前升级到 24.04，或采用 Ubuntu Pro 延长维护。

## 7. MySQL 起步参数与迁移前检查

建议以测试结果为准，从以下值起步：

```ini
[mysqld]
innodb_buffer_pool_size=4G
max_connections=100
character-set-server=utf8mb4
collation-server=utf8mb4_0900_ai_ci
default-time-zone=+00:00

log_bin=mysql-bin
binlog_format=ROW
binlog_row_image=FULL
binlog_expire_logs_seconds=604800
server_id=<大于1且唯一的整数>
```

迁移前必须对齐并记录：

- MySQL 精确版本、字符集、排序规则、时区和 `sql_mode`。
- `lower_case_table_names`、最大连接数、包大小和事务隔离级别。
- Django migration 状态。
- 表、索引、生成列、唯一约束、外键、视图、触发器和事件。
- 项目 RPA 持锁生成列及唯一索引。
- 所有表是否具备主键或真正唯一的唯一约束。

## 8. 迁移实施阶段

### 阶段 A：准备与冻结基线

1. 盘点源 VM 配置、数据库容量、峰值负载和依赖。
2. 固定迁移版本的 Git SHA、后端与前端镜像摘要。
3. 明确 RPO、RTO、负责人、维护窗口和停止条件。
4. 完成源数据库全量备份和独立恢复验证。

### 阶段 B：建设硅谷平行环境

1. 创建 VPC、交换机、安全组和两台按量 ECS。
2. 完成系统加固、补丁、SSH、监控、快照和备份配置。
3. 在数据库 ECS 安装并初始化同版本 MySQL 8.4。
4. 在应用 ECS 从硅谷 ACR 拉取固定摘要镜像。
5. 使用试点子域名和正式信任链 TLS 证书验证 HTTPS。

### 阶段 C：数据库全量与增量迁移

1. 配置源库 Binlog 和独立 DTS 账号。
2. 打通源网络到 DTS / 硅谷 VPC 的安全连接。
3. 执行 DTS 结构迁移、全量迁移和增量迁移。
4. 全量期间禁止 DDL，持续观察源库负载。
5. 完成表数、行数、关键业务汇总及抽样校验。

### 阶段 D：云上试点验证

1. 使用 `pilot` 子域名验证登录、权限、tenant 隔离和核心业务。
2. 验证 Celery、Redis、导出、审计、定时任务和幂等机制。
3. 从实际用户网络测试 HTTPS、API P95/P99、上传、下载和晚高峰丢包。
4. 执行备份恢复演练、故障演练、模拟切换及回退演练。
5. 云上环境连续稳定观察 7-14 天。

### 阶段 E：正式切换

1. 提前约 48 小时把 DNS TTL 调低至约 300 秒。
2. 冻结代码发布和数据库 DDL。
3. 停止旧环境 Celery Beat，暂停新任务产生。
4. 等待旧 worker 和队列完成或登记可重放任务。
5. 暂停业务写入，等待 DTS 增量延迟归零。
6. 执行最终数据校验。
7. 启动并验证新应用、Celery Worker 和 Beat。
8. 切换正式域名至 ALB 或新应用入口。
9. 开启新环境写入并进入重点观察。

### 阶段 F：观察与旧环境退役

- 旧 VM 保留 24-72 小时但禁止写入。
- 重点观察错误率、登录、Celery 队列、数据库连接、慢查询、磁盘和网络。
- 观察期通过后停止 DTS，删除临时迁移权限并归档证据。
- 旧环境在审批、备份保留和销毁计划确认后再下线。

## 9. Redis 与 Celery 切换要求

- Redis 缓存可在新环境重建，不要求原样迁移。
- Celery broker、结果和定时任务状态不能视为普通缓存直接丢弃。
- 切换时必须先停止 Beat，再停止任务生产，最后处理 worker。
- 对未完成任务建立清单，确认是否可重放、是否有幂等键。
- 新旧环境不得同时运行同一套 Beat，防止定时任务重复执行。

## 10. 验收门禁

正式切换前以下项目必须全部通过：

- [ ] VPC 网段无冲突，数据库无公网入口。
- [ ] SSH 密码登录和 root 远程登录已关闭。
- [ ] 固定镜像摘要、配置和数据库迁移版本一致。
- [ ] HTTPS 证书链受目标客户端信任，无证书警告。
- [ ] DTS 全量完成，增量延迟稳定并可在窗口内归零。
- [ ] 数据库表数、行数、关键汇总、生成列和唯一索引校验通过。
- [ ] 登录、角色权限、tenant 隔离、401/403、退出流程通过。
- [ ] Celery 队列切换及防重复执行验证通过。
- [ ] 数据库备份已在独立环境恢复成功。
- [ ] 模拟切换和回退演练通过。
- [ ] 中国内地或目标用户网络实测满足业务要求。
- [ ] 告警通知已验证，值班人员和联系人明确。
- [ ] 正式维护窗口及 Go/No-Go 审批完成。

## 11. 回退方案

### 11.1 新库尚未正式写入

若目标环境在只读验收阶段失败，可停止新应用，保持旧环境继续服务，无需进行数据反向处理。

### 11.2 新库已经正式写入

不得直接把域名切回旧应用并继续写旧库，否则会丢失新库期间产生的数据。必须执行以下之一：

1. 提前配置反向同步，经校验后切回；或
2. 暂停全部写入，导出新库增量变更并回放到旧库，校验后切回；或
3. 保持新库为唯一写库，仅回退应用版本。

实际切换计划应优先采用第三种：数据库切换完成后，应用问题通过回滚固定镜像解决，避免数据库往返切换。

## 12. 监控与扩容阈值

### 12.1 应用 ECS

- CPU 持续超过 70%：升级至 4 vCPU / 8 GB 或拆分 Celery。
- 可用内存持续低于 800 MB：扩容内存。
- Swap 持续读写：判定内存不足。
- Celery 队列持续积压：检查慢任务并扩容 worker。
- 系统盘达到 70%：清理日志、镜像或扩盘。

### 12.2 数据库 ECS

- CPU 持续超过 60% 或慢查询显著增加：评估 4 vCPU / 16 GB。
- 活跃连接接近 `max_connections` 的 70%：优化连接池并评估扩容。
- 长期发生 Swap：立即排查并扩容。
- 数据盘达到 70%：启动扩盘；达到 80%：停止非必要批量任务。
- I/O 延迟、锁等待或报表任务明显影响在线请求：优化查询或升级存储/规格。

## 13. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 中国内地访问硅谷延迟或丢包 | 页面与API体验不稳定 | 切换前实网测试；必要时评估全球加速或 ESA |
| 100 GB 数据盘容量不足 | DTS或生产写入失败 | 迁移前测量数据库、Binlog和增长；超过约40 GB改用200 GB |
| 单应用/单数据库节点故障 | 服务中断 | 自动快照、云备份、恢复演练；后续演进跨可用区高可用 |
| Celery新旧环境重复执行 | 重复任务或业务污染 | 先停Beat，清队列，核验幂等，禁止双Beat |
| 新库写入后直接回旧库 | 数据丢失或分叉 | 不直接回切数据库；采用反向同步或仅回滚应用 |
| MySQL参数或版本不一致 | 迁移、索引或查询异常 | 同版本部署，预检查并专项核验生成列和唯一索引 |
| 系统盘日志或备份占满 | 服务异常 | 数据目录分盘、日志轮转、备份外置、容量告警 |

## 14. 实施建议

1. 按量购买两台 ECS，先使用试点子域名建设平行环境。
2. 采购前确认当前数据库实际占用；不超过约 40 GB时采用100 GB数据盘，否则直接选择200 GB。
3. 数据库系统盘尚未购买时选60 GB；已经购买40 GB则保留并严格执行目录分盘。
4. 云上试点连续稳定7-14天且所有验收门禁通过后，再提交正式切换审批。
5. 正式切换后保留旧VM只读观察24-72小时，不立即销毁。
