## 功能修正

自动续期任务单独进入 `credential-refresh` 队列，由独立 `celery-credentials` worker 执行，并发 1、预取 1。保持每 60 秒扫描、到期前 15 分钟进入续期窗口，扫描消息 55 秒过期，避免独立队列长期堆积重复扫描。业务 worker 使用 round-robin 消费现有 `sync,celery`，不删除其他业务消息。

令牌轮换仍按平台、租户、授权记录和当前托管引用代次进行幂等认领。实际轮换前再次复核引用、权限及运行状态。仅“请求平台前的明确暂时失败”或“平台明确返回 429 限流”允许有限重试：最多 3 次尝试，60 / 120 秒退避。平台请求后超时、保存失败、旧版通用失败或进程失联均保留围栏，不能盲目重放可能已发生的令牌轮换。Lazada、TikTok 刷新 HTTP 请求关闭内部自动重放，Shopee 保持相同安全边界。

真实同步任务启动及每个分页边界检查续期状态。可自动恢复的授权临近到期时，持久化查询范围、游标、计数和续跑序号，释放任务执行锁，等待独立续期 worker；约 60 秒后由既有持久化调度继续同一运行。等待最长 30 分钟，不能无限循环。数据 worker 不直接刷新令牌，也不允许在正在使用旧令牌的页面中无锁轮换。

MySQL 1213 / 1205 使用独立的整页有界重试，最多额外 3 次；原始页归档、业务写入、分页游标、计数与最终检查点在同一事务中提交。事务回滚且游标不变时复用已获取的页，不再次调用平台。成功分页不重复入库；耗尽后保留原断点和固定脱敏错误。未提交的失败分页不会留下孤立原始页归档。

历史补采“重试可恢复失败分段”按当前授权、配置、只读准入及运行状态逐一筛选。已成功分段保持不变；不满足条件或对应任务正在运行的失败分段保留并跳过；无任何可恢复分段时拒绝无效操作。审计记录实际重试和跳过数量，不自动恢复已暂停的财务、退货退款批次。

页面显示专用续期扫描心跳、自动续期开关、当前授权有效期、最近实际续期、续期窗口及下一次退避时间。历史运行错误与当前授权/等待分段分别展示；授权恢复后历史失败不会自动消失。续期心跳只证明扫描实际开始，不证明各店铺成功。旧接口缺少字段时显示未知，不能伪造正常状态。

PRICE、FULFILLMENT、PAYMENT 等缺少独立检查链路的能力明确显示“本能力未接入独立检查”，说明读取开关不等于验证成功；不使用商品、订单或结算检查冒充独立能力检查。本版本不新增这些独立资源采集器、不新增广告路径，也不启用平台生产写入。

## 角色权限登记

不新增权限代码、菜单、角色自动授权或数据范围。权限目录及端点快照与 V214 一致。

| 权限 | 本版本对应能力 | 限制 |
| --- | --- | --- |
| `integrations.view` / 同步任务菜单查看权限 | 同步任务及专用续期状态展示 | 仅当前租户及已有配置、主体、资源范围 |
| `integrations.history.view` | 当前授权、等待分段及历史错误 | 只返回有权查看的店铺任务，不展示凭据引用或平台原始错误 |
| `integrations.history.manage` + `integrations.run_live_readonly` | 失败分段筛选重试、暂停、继续、创建 | 两种权限范围取交集；控制批次须覆盖全部任务，后台再核查原提交人权限 |
| `integrations.store.authorize` + `integrations.credential.rotate` | 店铺令牌自动续期资格与已有受控人工恢复 | 使用授权更新人的现有有效权限，平台/环境/地区/配置/店铺范围全部满足；不因“管理员”名称跳过校验 |
| `integrations.warehouse.authorize` | 极风仓库自动续期资格与已有授权操作 | 保留仓库、地区、配置范围和各地区实际 API Host；不替换为统一网址 |

系统管理员可按现有有效权限完成授权恢复和只读检查；只读用户不能重试、创建或控制批次。没有自动授予真实同步或生产写入权限。

## 迁移与部署审阅

新增 `integrations.0041_automatic_refresh_recovery`，只在 `AutomaticRefreshAttempt` 增加 `attempt_count`、`failure_category`、`next_retry_at` 三个字段；旧尝试默认保留，不清空、不将通用失败自动归类为可重试。代码回滚时保留前向兼容字段与审计，不反向删除数据。

部署不只更新镜像：须审核并安装新增消费者 Compose 和受控启动/健康检查清单，使用同一后端不可变镜像 digest，保持现有托管侧车、秘密文件挂载及网络约束。候选镜像覆盖应包括 `celery-credentials`，旧显式服务清单也不能遗漏它；无该服务的历史拓扑保持兼容。

建议发布顺序：审阅候选及最终提交 → CI 与不可变制品 → 虚拟机迁移、独立消费者和补采负载验证 → 阿里云同制品发布 → 新消费者订阅、心跳、授权期限及脱敏审计验收 → 再执行获准的业务恢复。每个环境验收后单独登记双账本，不把本地候选记录当作部署记录。

既有默认队列积压保留，由已有消费者继续处理；新扫描不再进入该队列。不清空整个 Redis/Celery 队列，不删除旧幂等围栏。先观察真实队列消退和 worker 状态，再决定是否另行授权定向处理陈旧扫描。

SP6TH 旧失败的具体轮换结果没有可证明的证据，保留人工恢复边界。发布后先读取托管元数据和审计，确认结果；不确定时经现有受控入口重新授权，再执行只读检查。授权/锁问题验证通过后，才重试可恢复失败分段。暂停的财务、退货退款批次继续保持暂停，需单独确认恢复。
