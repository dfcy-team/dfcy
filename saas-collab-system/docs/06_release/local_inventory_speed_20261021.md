# 库存菜单读取与计算提速（2026-10-21）

## 本轮调整

1. `decision_rows` 每次调用新建局部权限缓存，销量范围、库存范围、供应汇总、成本入口复用同次解析；预警接口也复用同一 HTTP 请求内的权限解析。缓存不保存到用户对象，不跨请求或后台批次复用。
2. 菜单快照行保存 SKU 排序键和是否有正数建议，使用覆盖筛选与排序的组合索引。无关键词查询不再为排序关联商品表，不再创建临时排序 B 树；关键词查询仍核对当前商品档案。
3. 分组汇总已经给出精确数量，分页复用该数量，去掉重复 COUNT；按剩余数量限制读取条数，空结果跳过数据查询。
4. 后台任务最多连续领取 10 轮、每轮两个视图块，每块最多计算 100 SKU。每轮结束后检查 3 秒预算，单轮计算不会被强制中断，因此这不是任务的硬性 3 秒上限。逐块保存结果并释放领取状态，避免每 100 SKU 固定等待下一轮 5 秒 Beat。多读取 1 个候选 SKU 判断是否有下一块，省去整百目录的空尾块。

计算公式、销量窗口、退款口径、来源有效性与授权边界保持一致。配对基准对每条计算结果执行相等检查。

## 验证方法

本地 SQLite，生成 1000 SKU、1000 条预警；每批计算 100 SKU，分页读取 20 条。批量造数后运行 ANALYZE；计算使用同进程同数据、交替运行的未缓存/优化路径，报告中位数。SQL 计划用 SQLite EXPLAIN QUERY PLAN 验证；PostgreSQL/MySQL 的正式库计划与端到端耗时未测。

完整迁移及后端回归：85 项通过；Django 系统检查、迁移一致性、git diff --check 通过。独立只读审查未发现本轮新增 P1/P2。

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 100 SKU 计算 SQL 次数 | 88 | 52 |
| 同进程配对计算中位数 | 82.798 ms | 53.208 ms |
| 20 行结果读取中位数（不含完整 API） | 8.216 ms | 0.676 ms |
| 补货菜单分页接口 SQL 次数 | 36 | 35 |
| 库存预警分页接口 SQL 次数 | 32 | 29 |

优化后完整分页接口中位数：库存决策 19.131 ms，库存预警 16.066 ms。不同运行轮次有主机负载波动，上表计算和行读取为同轮配对结果。执行计划显示使用 idx_inventory_row_state，取消了商品表主键关联及临时排序；正数建议路径使用 idx_inventory_row_positive。

可复现用例：`backend/tests/test_inventory_decision_speed.py`。原始聚合指标与计划保存于本机 `.codex-tmp/inventory-speed/verified-after.json` 和 `verified-after-alerts.json`，不含正式业务数据。

回归范围：计算结果一致性、零值与待核对分组、先筛选后分页、当前权限撤销、组织身份、后台策略切换、失联任务恢复、长构建有效期、自动解除与重开、索引迁移缓存失效、3 秒任务预算。

## 发布条件

新增 alerts 0007 迁移。旧快照缺少排序键和正数标志，迁移后标为待重建并提升版本，不修改或删除库存、销售及预警事实。PostgreSQL 使用非事务迁移和并发索引 DDL；其他引擎使用 Django 标准索引操作。发布时按既有流程执行迁移，并更新 worker/Beat 到同一版本。

本轮没有修改第三方 API 抓取频率或历史覆盖校验，没有向正式环境写入或部署。测量数据均为本地生成样本。
