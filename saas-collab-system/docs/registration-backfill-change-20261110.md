# GCash／推广历史补录调整

历史表格可能缺少退款原因、截图，金额也可能超出币种精度。旧导入直接拒绝这些记录；大批量预览模拟写库并回滚，确认时再次预览，易触发网关超时。

## 行为

- GCash 和推广批量页面增加默认关闭的“历史补录”。仅勾选后，金额使用 Decimal、ROUND_HALF_UP 按既有币种精度调整；例如 PHP 12601.4041 → 12601.40。GCash 空备注补为“历史补录，退款原因可能已缺失”，已有备注不覆盖。普通登记保持原精度及备注校验。
- 预览和详情显示原值、调整值；快照保存调整规则，推广登记／更正后仍保留。实际付款凭证与表格冲突时，应先修正源表再预览。
- GCash 导入及正式登记均允许无截图。填写截图文件名时仍须提供对应有效 PNG／JPEG；大小、数量和敏感信息权限保持原规则。
- 店铺字段支持当前租户内的编码或唯一全称，歧义拒绝；仍验证店铺权限与订单归属。分组去重使用规范店铺编码，切换编码／全称重试不重复创建。原输入内容变化仍报冲突，不因舍入后相同而静默忽略。
- 财务预览不创建登记、凭证或审计记录；页面每次处理20张登记，服务端分页上限40张。确认逐组提交，各页合并到同一批次；失败后保留原文件重做完整预览，已成功的记录识别为已存在。
- 导入仍只生成草稿，另行确认已付款；不执行转账，不自动确认线上历史草稿。未匹配订单仍需核对来源或同步订单。

## 接口与兼容

导入接口新增 `backfill=true|false`、`offset`、`limit`；响应增加 `total`、`next_offset`（末页 null）。原 `historical` 仅用于换货，不改变其语义。文件哈希绑定财务补录模式，切换模式必须重新预览；老客户端不传分页仍按原整批行为处理。

无模型及数据库迁移。未改线上记录、未给本次分配版本号。前后端需一起交付；普通构建仅用于验证，不作为正式发布制品。

## 验证与发布交接

后端使用隔离 SQLite 内存库和 `--nomigrations` 验证业务逻辑，不声称完成 MySQL 并发锁及生产超时性能验收。前端执行登记页面 Vitest 和禁用模拟模式的生产构建。具体验收见独立清单。

目标分支 main。正式系统当前是否处于统一发布、发布负责人和统一版本号尚待发布方确认；本次先提交新 PR。正式发布按 `docs/06_release/aliyun-release-notes.md` 的 prepare/build/confirm 流程生成制品并回读验证，不将本地构建登记为已上线。
