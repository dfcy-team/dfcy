# 独立平台达人档案与新建关联

## 第一版范围

- 一个账号对应一份完整 `Influencer` 档案，在列表中独立展示；同一平台可以创建和关联多个不同账号。
- 表单顶部的平台必填；已有档案的平台、昵称 ID 和已登记数字 ID 不因切换关联档案而改变。
- 昵称 ID 保存平台用户名，账号昵称保存平台真实展示名，两者独立填写。
- 系统档案编码由后端在保存新档案时自动生成，表单只读显示；不要求用户填写。历史及导入编码保持兼容，不重编旧档案。
- 从已有档案点击“新建关联档案”，创建同平台或其他平台的新账号档案，并与原档案建立双向可见的关联；不限制关联组中同平台的档案数量。
- 常规“新建达人”不建立关联。现有档案不自动匹配，不提供已有档案合并、关联组合并或拆分。
- 新建关联表单不复制原档案的用户名、数字 ID、联系方式、送样或建联记录。
- 联系渠道下拉保留邮箱、电话、WhatsApp、微信、LINE、Viber、其他；移除 Telegram、TikTok 私信、Instagram、Facebook Messenger 的预设选项。历史联系方式仍保留和显示，不自动删除或转换成达人档案。

## 业务边界

关联只用于人工确认后的导航，不共享身份字段、联系人、状态、统计数据或业务归因。

每份档案的送样、建联和绩效仍按原档案主键关联，不跨平台汇总，也不搬迁历史外键。
黑名单保留现有各档案规则和原 TikTok 同账号限制，不新增跨平台联动。
已经受限的原档案不能据此创建关联档案；这不替代独立平台档案的限制检查。

历史平台子账号表、记录及兼容接口保留。本次表单不提交 `platform_accounts`，避免普通档案编辑使旧子账号停用。没有子账号的历史档案不回填、不拆分。

## 接口

路径均相对于 `/api/internal/influencers/`，沿用现有成功响应封装。

| 操作 | 请求 | 返回 |
| --- | --- | --- |
| 完整表单读取 | `GET {id}/?include_form=true` | 完整当前档案，以及 `related_archives`、`archive_group_id`、`group_version` |
| 关联导航读取 | `GET {id}/related-archives/` | `results`、关联组 ID 和版本 |
| 新建关联档案 | `POST {source_id}/related-archives/`，请求体 `{ "archive": <完整新建档案内容> }` | 创建后的完整新档案和关联导航 |
| 普通创建、编辑 | 现有聚合表单接口 | 保留现有行为，不自动关联 |

导航摘要仅包含 `id`、`code`、`platform`、`nickname_id`、`account_nickname`、`updated_at`。
包含当前档案自身，未关联时只有自身；不返回其他档案的完整联系人、历史记录或身份摘要哈希。
普通默认列表和详情响应不增加这些敏感字段。关联读取要求内部有效用户的 `influencers.view + ALL`；完整表单和创建关联要求 `influencers.manage + ALL`，服务层也检查权限及租户。

## 提交与并发

新建关联请求必须提供原档案最新 `updated_at` 的 `If-Match`。
聚合编辑与新建关联中的 `If-Match` 缺失、格式错误、无效日期或无时区时，返回 `400` 和 `If-Match` 字段提示，不保存档案、联系人或审计变更；有效但过期的版本仍返回 `409`。
原档案版本过期返回冲突，不创建新档案。新档案必须选择受支持的平台，可以与原档案相同；原有账号身份冲突检查、权限和租户隔离保持不变。
关联建立、完整新档案保存、关联版本和所有受影响档案的更新时间、审计在一个事务内完成。
不调用平台 API，不启动抓取或归因任务，不修改原身份解析和送样归因函数。

若提交超时或结果未确认，保留原请求版本与表单，先按平台、昵称 ID 或账号昵称核对关联列表及档案列表。当前表单暂停重复创建。
不得自动刷新原档案版本后重复提交创建。使用旧版本重试应发生冲突，避免创建重复档案。
明确的字段校验失败不会提示创建结果不确定。主页信息按普通文字保存，不校验 URL 格式、不访问或抓取所填内容，可以填写数字、备注或链接，也可留空；最多 500 字符。兼容字段名仍为 `profile_url`，不搬迁旧内容。

## 部署与回退

新增关联组和成员表，迁移只添加结构，不执行历史业务数据回填。
本 PR 以当前 `main` 为基线，仅交付达人档案变更；不包含另一块 TikTok API 接入、授权续期、达人查询或数据暂存功能，也不需要先合并它们。

迁移链：`0026_sampleitem_warehouse -> 0028_influencer_platform_account -> 0029_primary_identity_indexes -> 0031_influence_archive_associations -> 0032_profile_reference_plain_text`。编号保留原开发记录，但不依赖 API 分支的 `0027` 或 `0030`。新增旧版兼容子账号表、关联组和成员表，以及可空身份摘要索引；主页信息迁移仅变更 Django 字段状态，不改变现有 varchar 列。

向 10 主机交付时，先核对实际运行提交及迁移记录，再执行正常应用迁移；不覆盖现场环境变量或手工数据。已有数据的租户必须先完成身份摘要补齐：用 `backfill_influencer_identity_indexes --tenant <tenant_id> --limit 500` 预览，再按批次加 `--apply`，直到 `remaining_parents` 和 `remaining_profiles` 均为 0。该步骤只补派生索引，不改原昵称、编码或业务时间；未补齐时新账号身份登记会主动拒绝，不能省略此步骤或以清空历史数据替代。

34 主机已是包含其他试验功能的部署版本，本 PR 的迁移依赖针对干净 `main`；不要直接覆盖已应用另一套依赖的 34 迁移文件。34 的后续整体升级需先比对迁移图并制定兼容合并。创建本 PR 不代表已部署 10 主机或阿里云服务器。
部署前备份并绑定实际运行镜像，验证迁移范围、业务数据不变量和服务健康。
现有冻结生产发布工具绑定了 `main` 已登记版本的迁移摘要；本 PR 保留该生产许可，不为达人新增迁移扩展批准范围或绕过门禁。新增迁移不能复用原批准包，正式生产发布应重新生成对应版本的验证证据和审批。
回退时停止关联入口并回退应用镜像，保留新增结构及已创建档案；不删除表或业务数据。

## 人工验收

1. 普通新建时必须选平台，未选择不能提交。
2. 从 TikTok 档案创建 Facebook 档案，填写独立昵称 ID、账号昵称、数字 ID 和联系方式。
3. 保存后列表出现两条独立档案；双方完整表单和详情能互相切换。
4. 修改新档案不改变原档案身份、送样和建联记录。
5. 普通新建相似昵称不自动关联历史档案。
6. 未保存修改时切换会提示确认；取消后修改仍保留。
7. 重复点击提交或请求结果不确定时，不自动重复创建。
8. 从 Facebook 档案连续新建多个 Facebook 账号，保存后各自独立且相互可见；使用最新原档案版本提交。
9. 关联区的新建按钮与外部“新建达人”使用相同的实心主按钮样式。
10. 搜索昵称 ID 和账号昵称均能找到对应档案；历史相同值保留并标注待核实。
11. 主页信息填写普通文字或数字也能保存；已保存的旧联系渠道不因选项调整而丢失。
