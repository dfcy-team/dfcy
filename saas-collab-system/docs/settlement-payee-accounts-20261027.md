# 供应链结算收款账户调整

适用：费用与结算中的供应商发货单货款、集货发运批次运费。

操作：打开费用与结算 → 结算登记 → 管理收款账户，新增本供应商或货运公司的账户名称、收款户名、开户银行、账号和对公/对私性质。登记累计已结算金额并选择账户，账户自动带出性质；多个账户各填累计金额，合计必须等于本单据累计已结算金额。保存后继续使用原历史结算行上传付款凭证。

本系统现有结算是累计金额的版本登记，不是每次付款流水。每次修改需提交全部账户累计分配，不能把多次累计金额相加。账户性质本身不修改商品成本；已确认采购价格、费用及既有成本版本计算仍是成本依据。

历史记录：未登记账户的旧记录保持未标识；每个新结算版本冻结账户信息，修改档案不改写旧版本。原账户停用后只允许保留既有累计分配，不得新增或增加停用账户分配。

商品成本查询分别显示货款、运费结算性质，来自当前来源发货单和发运批次；查看历史成本版本时仍明确标注当前结算口径。混合结算是单据级分类，不能据此认定某个SKU或某件商品已经独立指定对公/对私。具体商品行分配属于后续独立需求。

性能：账户列表用户展开或管理时按需加载，单业务对象最多100个；金额校验使用4位小数整数单位；商品成本分页批量读取结算信息，避免每商品发账户请求。

权限：账户创建编辑需现有供应链管理权限，读取受单据租户和数据范围限制；仅可选择对应供应商或货运公司的账户。历史展示账号掩码；无管理权限不能修改账户或结算。

发布：此交付为本地候选，未部署。新增供应链迁移0031；与另行供应链附件对象存储候选的0031编号冲突，发布整合必须按最终累计基线重编号或合并迁移叶节点，不可遗漏任一变更。禁止直接覆盖线上源代码或自动补写历史账户性质。

验证：后端成本/结算/付款凭证相关测试34项通过，新增迁移在正常本地测试库实际执行成功；Django check无问题，makemigrations --check无差异。前端账户、结算、凭证、商品成本查询相关测试32项通过，生产构建通过。审查发现的历史性质显示不一致和账户强制刷新竞态已修复并补测试。未进行正式系统或虚拟机写入，也未进行真实银行转账。
