# 供应链完整需求基线 V2 变更包

- 编号：`SCM-REQ-V2`
- 日期：2026-08-08
- 状态：`BASELINE_FROZEN_FOR_INDEPENDENT_REVIEW`
- 适用环境：仅架构员主机、本地分支和本地数据库
- 禁止事项：不得连接、迁移、写入或切换供应链正式线上系统

## 1. 决策结论

本变更包将下列内容正式纳入供应链融合需求基线：

1. 技术架构沿用现有 SaaS 协同系统：Vue 3 管理端、Django/DRF 后端、MySQL 8、原生微信小程序；不引入原供应链附件中的 React/Taro/Supabase 运行架构。
2. 权限沿用协同系统的租户、角色、权限、用户角色、DataScope 和审计体系；业务角色名称只作为角色模板，不作为代码中的授权判断。
3. 采购订单正式支持部分装箱、多个装箱批次并行或先后完成，以及一次订单分多次发货。
4. 采购订单创建时不要求确定散货或柜货；生产完成后，由具有权限的后端采购人员确定订单运输路线。
5. 散货不是快递直发。供应商完成装箱批次后，由后端采购按区域归集不同供应商的已完成批次，指定具体集货地点，再与其他公司货物在该地点拼柜、报关并统一出货。

## 2. 与历史基线的关系

本文件不删除或改写历史审核记录。冲突时，以本文件及其后续独立审核通过版本为准。

| 历史规则 | V2 处理决定 |
| --- | --- |
| 一个订单最多一个活动装箱批次 | 被替代；一个订单允许多个批次，但必须通过数量占用和并发锁防止重复装箱 |
| 装箱批次完成必须覆盖订单全部明细数量 | 被替代；批次完成只表示本批次箱明细完整且冻结，不等于整单已全部装箱 |
| 散货由供应商上传快递单后进入到仓/清货 | 被替代；改为区域集货、拼柜、报关、统一出货，并继续承接到仓与清货节点 |
| 柜货/散货在采购下单时确定 | 继续废止；生产完成后由采购指定 |
| Supabase/RLS 或硬编码角色控制权限 | 不准入；统一使用现有协同系统权限与 DataScope |

受影响但保留为历史证据的文件包括：

- `scm_f2_0_packing_domain_contract.md`
- `scm_post_production_shipping_route_requirement_addendum.md`
- `scm_shipping_route_1_*`

## 3. 业务边界

### 3.1 系统内权威数据

本系统对以下数据负责：

- 本企业采购订单及其明细；
- 本企业供应商及供应商账号绑定；
- 本企业货物的生产完成数量、装箱批次、箱明细和附件；
- 本企业货物的集货分配、集货地点、交接证据和物流状态；
- 与本企业货物相关的拼柜、报关、发货、到仓、清货引用编号和状态；
- 所有关键动作的操作者、租户、时间、请求幂等键、前后版本和审计事件。

### 3.2 系统外数据

“其他公司货物”的订单、商品、供应商和箱明细不进入本系统。本系统只保存承运商或货代提供的外部拼柜号、柜号、报关号、运输号及与本企业货物相关的必要总量引用，避免扩大数据权责边界。

### 3.3 人工审批点

- 生产完成后，采购决定订单为 `loose_cargo` 或 `container`。
- 散货批次完成后，采购按区域和实际集货安排选择集货地点并确认归集。
- 集货收货、拼柜、报关、发货、到仓和清货均由对应权限人员确认，不由系统基于时间自动越级推进。
- 路线、批次或发运已经被下游业务消费后，修改必须走受控撤销/更正流程，禁止直接覆盖历史数据。

## 4. 目标业务流程

### 4.1 共同前段

`采购订单 -> 供应商接单 -> 生产中 -> 生产完成 -> 采购指定运输路线`

路线必须在生产完成后、首个下游发运归集动作前确定。同一采购订单的所有装箱批次继承同一路线；若需要拆分路线，必须先拆分为独立订单或通过后续经过审核的显式拆单能力处理。

### 4.2 部分装箱与多批次

1. 供应商可针对订单部分明细数量创建装箱批次。
2. 同一订单可存在多个草稿、装箱中或已完成批次。
3. 创建、修改、完成或取消批次时，系统必须核对“生产可用数量、已占用数量、已装箱数量”，禁止超量或重复占用。
4. 批次完成后冻结批次版本、箱明细、数量和标签输入；后续更正生成新版本或受控撤销记录。
5. 订单层展示累计生产、已装箱、待装箱、已发货、待发货、已到仓和已清货数量，不再用单一批次代表整单履约。

数量权威源与守恒规则：

- 权威计量单位沿用采购订单明细单位；包装规格、箱数、重量和体积是物流属性，不替代采购数量。
- 每条订单明细始终满足：`生产完成量 >= 已冻结装箱量 >= 已发货量 >= 已到仓量 >= 已清货量 >= 0`。
- `装箱占用量` 只用于未完成批次的并发预留；`装箱占用量 + 已冻结装箱量 <= 生产完成量`。
- 订单汇总只能由不可变履约事件/台账计算，不允许客户端直接写累计字段；缓存字段必须能从台账重建并定期对账。
- 取消未完成批次释放占用量；已完成批次不得直接取消，必须通过带原因和反向台账事件的受控撤销。

### 4.3 散货区域集货

`已完成装箱批次 -> 待集货分配 -> 采购按区域归集 -> 指定集货地点/截止时间 -> 供应商交货或提货 -> 集货点收货 -> 与外部货物拼柜 -> 报关 -> 统一发货 -> 到仓 -> 清货`

约束：

- 一个集货单可包含多个供应商、多个采购订单和多个已完成批次。
- 只有同租户、散货路线、区域/地点/时效兼容的批次可以进入同一集货单。
- 一个已冻结的箱或数量分配不得同时被两个有效集货/发运记录消费。
- 一个装箱批次可以进入多次发运，但已封箱后以“完整箱”为最小物理分配单位；同一箱不得拆到两个有效集货单或发运单。若实际需要拆箱，必须先执行受控拆箱/重新装箱，生成新批次版本及审计事件。
- 集货地点必须是受控主数据，至少包含编码、区域、地址、联系人、时区、启停状态和生效时间。
- 供应商只能看到与自身订单/批次有关的集货地点、截止时间和交接要求，不得看到同集货单其他供应商的商业数据。

### 4.4 柜货

柜货继续走本企业货物装柜路线：

`已完成装箱批次 -> 装柜计划 -> 装柜确认 -> 报关 -> 发货 -> 到岸/到仓 -> 清货`

柜货和散货可复用后段报关、运输、到仓、清货领域能力，但集货单与本企业装柜计划必须保持不同聚合根和不同授权动作。

### 4.5 多次发货

- 一张采购订单可以由多个发运单履约；一个发运单可以引用多个订单的已完成箱或数量分配。
- 发运状态在发运单层独立推进，订单层状态由履约台账汇总派生。
- 推荐保留订单主生命周期并新增履约摘要，如 `partially_packed`、`fully_packed`、`partially_shipped`、`fully_shipped`、`partially_received`、`fully_cleared`，避免多个发运单反向覆盖订单主状态。

每个状态动作都必须冻结“允许前态、执行主体、所需证据、幂等结果和撤销方式”。采购负责路线、区域归集和地点分配；供应商负责装箱及交接证据；物流/报关人员负责集货收货、拼柜引用、报关和发货；仓库负责到仓及清货。一个角色可以由同一用户兼任，但授权校验仍按动作逐项执行。

## 5. 领域与数据改造范围

### 5.1 必须改造

- 将现有“每订单一个活动批次”的唯一约束替换为明细数量占用、箱分配和版本约束。
- 增加订单明细履约台账：生产完成量、装箱占用量、已装箱量、已发货量、已到仓量、已清货量。
- 增加集货地点、散货集货单、集货批次/箱分配、发运单、发运箱/数量分配及状态事件。
- 增加外部拼柜、柜号、报关和承运引用字段，但不导入其他公司货物明细。
- 所有计数和状态变更使用事务、`select_for_update`、确定性加锁顺序、乐观版本和幂等键。
- 任何 ORM、批量更新或后台任务入口都必须复用领域服务或数据库约束，不得绕过租户、数量和状态校验。

### 5.3 既有数据迁移原则

- 现有 `PackingBatchOrder.active_guard` 和单活动批次唯一约束在新约束生效前不得直接删除。
- 先只读盘点每个订单的活动/完成/取消批次、箱明细和数量差异；异常数据进入人工清单，不自动猜测修复。
- 合法既有批次生成初始履约台账和箱分配身份；迁移必须可重复执行、带校验摘要，并在事务外提供可验证回滚方案。
- 采用“新增表/字段 -> 双读校验 -> 本地回填 -> 新服务切换 -> 旧约束退役”的波次，不允许一次迁移同时删旧约束并切换全部写入口。
- 本机迁移必须验证零数据、单批次、多历史批次、取消批次、超量异常以及回滚；生产迁移另行立项和审批。

### 5.2 建议聚合

| 聚合 | 核心职责 |
| --- | --- |
| `PackingBatch` | 本次装箱的箱、数量、标签输入和冻结版本 |
| `ConsolidationSite` | 区域集货地点主数据 |
| `LooseCargoConsolidation` | 采购按区域归集散货批次并安排集货 |
| `Shipment` | 一次实际统一发货及后续物流节点 |
| `FulfillmentLedger` | 订单明细各履约阶段的不可重复数量台账 |
| `DomainEvent/OperationLog` | 关键动作审计、幂等结果和并发追踪 |

最终模型名可在领域契约审核中调整，但职责边界不得合并为单一“大物流表”。

## 6. 权限与 DataScope 基线

### 6.1 授权原则

- 内部网页端和内部小程序端：`租户有效成员 + Permission + DataScope + 对象状态` 四层校验。
- 外部供应商小程序端：`外部用户类型 + supplier binding + 订单/批次归属 + 对象状态 + 专用 capability`；不得给供应商账号分配内部角色来绕过绑定。
- 路由层默认拒绝，未声明权限和 DataScope 的供应链接口不得发布。
- 数据过滤与对象动作校验必须同时存在；只隐藏按钮不构成权限控制。

### 6.2 权限码变化

继续使用现有 `supply.purchase_order.*`、`supply.production.*`、`supply.packing.*` 和 `supply.purchase_order.assign_shipping_route`。后续契约审核拟新增：

- `supply.consolidation.view/create/update/allocate/release`
- `supply.shipment.view/create/dispatch/update`
- `supply.customs.confirm`
- `supply.warehouse.arrival.confirm`
- `supply.warehouse.clearance.complete`
- `supply.evidence.view/review`

拟新增 DataScope 维度：`supplier_ids`、`supply_purchase_order_ids`、`packing_batch_ids`、`consolidation_site_ids`、`consolidation_ids`、`shipment_ids`。具体命名必须在 API/权限契约审核后冻结。

## 7. Web 与微信小程序职责

### 7.1 Web 后台

- 采购：路线指定、区域归集、集货地点选择、截止时间和异常处理。
- 物流/报关：集货收货、拼柜引用、报关和统一发货确认。
- 仓库：到仓、清货确认。
- 管理：集货地点主数据、权限、DataScope、审计查询。

### 7.2 微信小程序

- 供应商：查看订单、部分装箱、多批次维护、标签、查看集货安排、提交交接证据。
- 授权内部人员：按权限查看或确认移动场景动作；不能因在小程序渠道就弱化权限或 DataScope。
- 网络、媒体、PDF 标签、输入框、安全区和键盘行为必须同时通过 Android 与 iPhone 真机门禁，详见 `scm_miniapp_ios_android_compatibility_baseline.md`。

## 9. 验收指标

- 同一订单可建立多个合法装箱批次，任何并发路径均不能超订单明细可用数量。
- 同一箱或同一数量份额不能被多个有效集货单/发运单重复消费。
- 散货可按区域、供应商、批次和集货地点查询并形成完整审计链。
- 采购、物流、仓库和供应商账号只能看到并操作授权范围内对象。
- 重复请求返回相同结果；冲突请求明确失败且不产生部分写入。
- 订单履约汇总等于台账之和，并可追溯到批次、箱、集货和发运记录。
- Android 与 iPhone 真机均能完成装箱、标签、集货查看和证据上传主流程。
