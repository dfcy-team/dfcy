# SCM-FUSION-REVIEW-001 供应链业务功能首次融合审核包

> 状态：`PREPARED_FOR_REVIEW`（待首次审核，尚未授权实施）

> 审核对象：供应链网页端、小程序端业务能力向现有协同系统的融合方案
> 执行环境：仅限架构员主机、本地开发环境

> 源系统参考：React/Vite 网页端、Taro 小程序端、Supabase 数据模型与函数

## 1. 审核目的

本次审核不是生产上线审核，也不是全量数据迁移审核。审核目标是：

1. 确认供应链业务能力应如何映射到现有协同系统。
2. 确认系统、数据、安全、客户端和实施边界。
3. 决定是否仅授权第一批低风险本地融合工作包 `SC-F1`。
4. 为后续装箱、货柜、财务、通知、数据迁移和生产切换建立独立审核入口。

本文件经会议签署前，仅代表建议方案，不代表已获得开发、迁移或上线授权。

## 3. 总体融合结论建议

### 3.1 采用“业务能力重构映射”，不采用“源系统原样合并”

源 React/Taro/Supabase 项目仅作为业务需求与历史行为来源：

```text
源网页端 / 源小程序 / Supabase
             │
             │  提取业务语义、字段、状态、规则、证据
             ▼
Vue 3 / 原生小程序 → Django/DRF → MySQL 8
                         │
                         ├─ Redis/Celery
                         ├─ Files/Object Storage
                         └─ Audit/Alerts/Integrations
```

不执行以下做法：

- 不把 React 网页端直接嵌入 Vue 管理端。
- 不把 Taro 工程直接覆盖或并入现有原生小程序。
- 不保留客户端直连 Supabase 的目标架构。
- 不将 Supabase SQL 迁移文件直接转换后执行到目标 MySQL。
- 不把 Supabase RLS 当作目标系统权限方案。

### 3.2 Supabase 与 MySQL 的处理决定建议

目标协同系统应统一收敛到 MySQL 8，但这不等于立即转换或替换线上 Supabase：

1. 本地功能融合阶段先在 Django/MySQL 中建立目标领域模型和 API。
2. 使用脱敏、虚构或专门构造的数据验证业务行为。
3. 后续单独设计可重复、可校验、可回滚的数据迁移程序。
4. 生产 Supabase 在完成迁移演练、对账和切换审核前保持原状。
5. 生产切换必须另行审核，不属于 `SC-F1`。

## 8. 目标领域模型原则

### 8.1 采购单模型

现有 `purchasing.PurchaseOrder` 更接近“单行采购记录”，而源供应链采购单是“一张单头包含多条明细”。首次融合不得通过增加大量可空字段或把多条明细压缩成 JSON 来覆盖现有模型。

建议在 `purchasing` 中新增版本化聚合，例如：

- `SupplyPurchaseOrder`：采购单头、供应商、租户、状态、日期、金额汇总和源记录信息。
- `SupplyPurchaseOrderLine`：SKU、数量、单价、交期和行级生产信息。
- `SupplyProductionProgress`：进度值、说明、操作人和时间。
- `LegacyRecordMap`：源系统、源表、源 ID、目标模型和目标 ID。

最终命名可在 F0 冻结，但必须遵守：

- 不破坏旧模型和旧接口。
- 单头/明细保持关系型结构。
- 状态变更只能通过领域服务/动作 API。
- 所有业务记录显式包含租户归属。
- 所有供应商操作执行租户和供应商双重范围校验。

### 8.2 状态机

源采购单状态包含：

```text
pending → accepted → in_production → production_completed
        → ready_to_ship → shipping_review_pending → shipping → shipped
```

`SC-F1` 只实现到 `production_completed`。后续物流状态由 F3 接管。

要求：

- 状态转换白名单化，拒绝任意状态赋值。
- 状态动作在 `transaction.atomic()` 中完成。
- 同时记录操作者、租户、供应商、前后状态、请求 ID 和时间。
- 重复动作必须幂等，冲突返回明确错误。
- 禁止通过批量更新绕过领域服务和审计。

## 9. 数据转换与映射规则

### 9.1 主键与源记录

源 Supabase 记录多使用 UUID，目标系统主要使用 BigAutoField。不得强制把 UUID 改造成目标主键。

目标记录应保留：

- `source_system`
- `source_table`
- `source_record_id`
- `source_updated_at`
- 可选 `source_payload_hash`

同一 `source_system + source_table + source_record_id` 必须唯一，以支持幂等导入和追踪。

### 9.2 租户与供应商

- 每条目标业务数据必须获得明确 `tenant_id`。
- 无法确认租户的数据进入隔离错误集，不得自动归入默认租户。
- 供应商通过受控映射表与 `SupplierMaster` 关联。
- 无法唯一匹配的供应商必须人工裁决，不得只按名称模糊合并。

### 9.3 身份与敏感字段

- 不迁移 Supabase Auth 密码、Token 或会话。
- 不以明文保存 OpenID/UnionID。
- 微信身份绑定采用现有小程序身份体系重新建立。
- 源配置中的 Secret 只列为风险证据，不进入代码、文档或测试数据。

### 9.4 类型与语义

- 时间统一按 UTC 存储，界面按用户时区展示。
- 金额、成本和数量使用明确精度的 `Decimal`，禁止使用浮点数迁移。
- 枚举必须建立显式映射表，未知值进入异常队列。
- JSON 字段应拆分为稳定结构；确需保留时定义 schema 和版本。
- 文件只迁移元数据映射；真实对象迁移属于 F3/F5。

### 9.5 迁移程序

后续迁移程序必须：

- 可重复执行且结果幂等。
- 支持 dry-run。
- 支持分批、断点和失败重试。
- 记录每条源记录的处理结果。
- 输出记录数、关键金额/数量汇总、异常数和哈希对账。
- 在生产运行前至少完成两轮脱敏数据演练和一次回退演练。

## 10. API 与客户端边界

建议的路由归属：

| 使用方 | 路由边界 | 规则 |
|---|---|---|
| 内部 Vue 管理端 | `/api/internal/purchasing/` 或冻结后的 `/api/internal/supply-chain/` | 内部角色与 DataScope |
| 供应商门户 | `/api/external/supplier/` | 只允许当前供应商数据 |
| 原生微信小程序 | `/api/miniapp/supply-chain/` | 使用现有小程序会话和请求规范 |
| 财务 | `/api/finance/` | F4 后单独开放 |
| 报表 | `/api/report/` | 只读、租户隔离 |

共同要求：

- 客户端不得直连 MySQL 或 Supabase。
- 客户端不得持有 Service Role 或数据库高权限凭据。
- 动作 API 采用明确动词，例如 `accept`、`start-production`、`update-progress`、`complete-production`。
- 写操作使用请求 ID 和幂等键。
- 错误响应不得泄露其他租户或供应商对象是否存在。
- 所有列表和详情查询在服务端施加租户/DataScope/供应商过滤。

## 11. 权限与审计基线

建议冻结的最小权限代码：

- `supply.purchase_order.view`
- `supply.purchase_order.create`
- `supply.purchase_order.accept`
- `supply.production.start`
- `supply.production.update`
- `supply.production.complete`

权限规则：

- 内部用户按租户、角色和 DataScope 授权。
- 供应商用户只能查看和操作绑定供应商的采购单。
- 超级管理员能力不能下放给普通业务账号。
- 前端按钮控制只负责体验，不作为安全边界。
- 领域动作写入不可变审计记录。

源系统中存在范围过宽的 RLS、匿名附件访问、Service Role 函数对象级授权不足，以及安全函数未固定 `search_path` 等历史风险。目标实现不得复制这些策略。

## 19. 审核结论模板

可选结论：

- `PASS`：D1-D10 已批准，P0=0，允许启动本地 `SC-F1`。

- `FAIL`：存在 P0、系统边界未确认或核心模型决策未形成结论。
