# SCM-REQ-V3-R1 供应链完整需求基线独立审核

- 审核编号：`SCM-REQ-V3-R1`
- 日期：2026-08-10
- 审核对象：`scm_requirement_baseline_v3_full_scope.md`、`scm_requirement_v3_traceability_matrix.md`
- 业务来源：桌面目录两份最新完整需求文件
- 审核范围：需求覆盖、权威层级、技术适配、状态/实体冲突、安全门禁和实施可执行性
- 审核结论：`BLOCKED_PENDING_P1_REMEDIATION`

## 1. 总体结论

V3 已正确完成以下基线调整：

- 两份桌面文件被声明为最新完整业务需求来源；
- 网页端主要模块、小程序页面树、业务规则、实体、非功能要求和验收范围均已进入追踪；
- React/Taro/Supabase 实现描述没有被错误引入现有协同系统；
- Vue 3、Django/DRF、MySQL 8、原生微信小程序、Permission/DataScope 和审计被保留；
- 多租户、数量守恒、并发、幂等、附件安全、同箱防重和正式系统隔离没有被弱化；
- 当前实现与完整需求之间的大量缺口没有被误报为已完成。

但当前文档仍不足以作为可直接编码的冻结合同。存在 5 项 P1 和 3 项 P2。P1 关闭前不得进入 `SCM-V3-MAP-1` 实现或业务代码修改。

## 2. P1 问题

### SCM-REQ-V3-R1-P1-001：权威源未按内容摘要冻结

V3 只记录绝对路径，没有记录文件大小、修改时间和 SHA-256。桌面文件可被原位修改，后续无法证明审核、开发和验收使用的是同一版本。

整改要求：

- 在 V3 记录两份源文件的文件名、大小、修改时间、SHA-256 和编码检查结果；
- 定义源文件变化后的重新基线流程；
- 追踪矩阵记录对应基线版本，不仅记录目录名称。

### SCM-REQ-V3-R1-P1-002：完整需求尚未形成逐条稳定标识

追踪矩阵按章节或验收区间合并，例如 `9.11-9.30`，不能定位单条需求的设计、代码、测试和验收证据。网页端大量字段、按钮、公式和供应商评级验收也只按模块汇总。

整改要求：

- 给网页端功能/规则/验收和小程序 81 条验收分配稳定 Requirement ID；
- 至少记录：源章节、需求摘要、适用端、当前状态、领域/API/客户端、测试证据、目标波次；
- 一条需求包含多个独立动作时拆分为可验证条目。

### SCM-REQ-V3-R1-P1-003：两份最高权威源之间缺少冲突裁决规则

两份文件被设置为同一最高优先级，但订单、装箱、发货、货柜及技术章节存在重叠。当前只说明“以两份文件为最高权威”，没有定义二者互相冲突时如何处理，也没有冲突登记表。

整改要求：

- 业务冲突不得由开发人员自行选择；统一登记为 `UNRESOLVED`；
- 明确页面专属需求由对应端文件解释，共享状态、数量和权限由后端领域合同统一；
- 每项冲突记录候选方案、影响数据、兼容策略和最终决策人。

### SCM-REQ-V3-R1-P1-004：散货、区域集货、柜货及路线决定时点未唯一冻结

最新小程序需求描述散货上传货运单、出货审核后直接发货；既有 V2 和当前实现描述生产完成后采购决定路线、散货按区域集货并与外部货物拼柜统一出货。V3 将两者同时保留为子流程，却没有冻结：

- 下单时还是生产完成后决定路线；
- 散货直发与区域集货是互斥模式、前后阶段还是不同业务类型；
- 哪类主体有权选择模式；
- 货运单、交接证据、集货收货和发运的前置关系；
- 已有订单和批次如何迁移。

整改要求：建立唯一的路线/模式决策表、动作权限、状态前置条件和迁移规则。在该合同冻结前不得修改现有路线或发运模型。

### SCM-REQ-V3-R1-P1-005：四组状态机与当前领域状态尚无可执行映射

源需求包含采购订单 8 态、发货单 5 态、货柜 9 态及装箱 `admin_status`；当前系统同时存在采购状态、明细履约投影、PackingBatch、Consolidation 和 Shipment 状态。V3 只标记“需重构”，没有定义权威状态、派生状态、动作、允许前态、证据、撤销和历史迁移。

整改要求：

- 分别建立 Order、Packing、Shipment、Container/Consolidation 状态映射表；
- 区分权威写状态与只读派生展示状态；
- 多批次、多发货不得通过最后写入覆盖订单状态；
- 定义旧值迁移、未知值隔离、回滚和审计事件；
- 映射通过独立审核后才能进入模型/API修改。

## 3. P2 问题

### SCM-REQ-V3-R1-P2-001：当前状态缺少可复核证据路径

矩阵使用“已实现/部分实现”等判断，但多数条目没有对应模型、API、页面、迁移、测试和审核文档路径。后续应补 Evidence ID/路径，防止恢复分支再次发生实现状态误判。

处理决定：在 P1 逐条矩阵中一并增加证据列；无证据一律不能标记“已实现”。

### SCM-REQ-V3-R1-P2-002：Android/iPhone 门禁没有设备矩阵模板

V3 已提出真机门禁，但没有最低设备/系统/微信版本、证据文件命名、通过条件和缺陷回归模板。

处理决定：在进入 `MINIAPP-CORE` 前建立独立兼容性矩阵；开发者工具和单元测试不得替代真机结论。

### SCM-REQ-V3-R1-P2-003：完整需求包仍缺少可移交索引

桌面目录只有两份正文；API合同、权限矩阵、数据映射、状态图和验收证据分散在仓库审核目录。

处理决定：P1 关闭后新增 V3 文档索引，列出每个后续合同、审核、实现和验收归档位置。不得复制密钥、凭据或生产数据到需求包。
