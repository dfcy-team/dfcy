# API 平台分层第四阶段实施说明（2026-09-02）

## 目标与操作员

面向平台接入管理员：当历史店铺需要补齐平台站点或新授权需要配置读取能力时，把人工查表、逐条修改和来源判断变成可预览、可确认、可审计的流程，目标是降低错绑与越权同步风险，并缩短单批配置时间。

本阶段只覆盖 L1 只读分析和 L2 变更集确认，不开启平台写入、自动授权或自动切换凭据。

## 输入 → 决策 → 输出

1. 历史店铺映射工作台读取待关联店铺及候选站点，展示 exact、ambiguous、unmatched 和前后快照。
2. 操作员只能勾选 exact，二次确认后提交 `confirmed=true + store_ids + idempotency_key`。
3. 能力矩阵根据平台注册表生成只读建议；建议先载入本地表单，操作员复核 scopes/evidence 后再保存。
4. 实时只读同步按同店铺、同能力的 `source_priority` 升序选择来源；相同优先级按授权 ID、能力 ID 稳定排序。
5. 新同步运行创建后写入 `sync_source_selected` 操作日志，记录候选、选中授权、能力及优先级。

## 安全和决策规则

- 映射工作台不创建站点、不覆盖已有站点，不允许选择 ambiguous 或 unmatched。
- 后端在提交时重新计算匹配，避免预览后数据变化造成错误写入。
- 能力建议只来源于后端 `CAPABILITY_REGISTRY` 中明确支持 `live_readonly` 的资源。
- 平台注册表不能证明 OAuth scopes 已真实授予，因此建议统一标记 `scope_verification=unverified`、`confidence=medium`。
- 建议不会自动落库；现有能力 PUT 是人工批准边界。
- 所有建议和保存负载的 `write_enabled` 均为 `false`。
- 同步任务绑定的授权不是排序后的首选来源时，以 `CAPABILITY_SOURCE_NOT_SELECTED` 失败关闭，不自动改绑凭据。

## 范围标签

- `[U 通用]`：映射预览、幂等确认、候选来源排序、审计日志。
- `[P 部分通用]`：资源类型到能力代码、同步方式与平台支持度，由平台注册表和适配器承载。
- `[X 平台专属]`：OAuth scope 名称及平台权限语义；本阶段不猜测，保留人工核验。

## 验证指标与两周观察

- 主指标：20 条历史店铺的 exact 映射从预览到确认完成时间，相比逐条编辑降低至少 50%。
- 护栏一：已有关联站点被覆盖数量必须为 0。
- 护栏二：未核验 scopes 的建议自动落库数量必须为 0；平台写入能力启用数量必须为 0。
- 样本：至少 20 条历史店铺、5 个有效店铺授权、每个可执行资源至少 3 次只读运行。
- 停止条件：出现跨租户候选、非 exact 被应用、来源决策未记录、或任何 `write_enabled=true`。

## 上线与回滚

1. 先发布后端建议字段与来源审计，再发布前端工作台；无数据库迁移。
2. 首批只选择 5 至 20 条 exact 记录，导出预览并保存操作日志。
3. 能力建议逐授权人工确认，先验证 ORDER/RETURN_REFUND 等已存在只读适配器的资源。
4. 回滚前端不会影响既有映射和能力数据；回滚后端时保留操作日志。
5. 如来源门禁造成任务停止，应修正授权状态、能力状态或优先级，不删除审计记录，也不绕过凭据托管规则。

## 验证结果

- 第四阶段及相邻平台分层后端定向测试：10 项通过；最终变更子集复核：7 项通过。
- 店铺主数据前端定向测试：11 项通过；`StoreMasterList.vue` 单文件组件编译通过。
- Django system check 通过；`makemigrations --check --dry-run` 无待生成迁移。
- 完整前端构建仍被存量产品模块阻断：`src/api/products.js` 引用了 `src/mock/products.js` 未导出的 `mockProductDetailList`。该问题不在本阶段文件范围内，本阶段未修改或规避它。

## 明确不在本阶段

- 不调用真实平台写接口。
- 不根据字符串猜测平台 OAuth scope。
- 不自动处理 ambiguous/unmatched 映射。
- 不自动创建、刷新或切换授权凭据。
- 不新增独立菜单或宽泛分析看板。
