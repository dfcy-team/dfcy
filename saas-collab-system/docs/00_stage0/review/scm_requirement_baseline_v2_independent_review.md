# SCM-REQ-V2-R1 供应链完整需求基线 V2 独立审核

- 审核编号：`SCM-REQ-V2-R1`
- 日期：2026-08-08
- 审核对象：`scm_requirement_baseline_v2_change_package.md`、`scm_miniapp_ios_android_compatibility_baseline.md`
- 审核范围：业务边界、数量守恒、并发消费、历史迁移、权限、外部数据边界及双端小程序门禁
- 审核方式：本机静态独立审核；未运行迁移、未修改业务代码、未连接线上系统
- 结论：`PASS_WITH_P1_REMEDIATED_LOCALLY`

## 1. 模型路由执行记录

- 主代理负责需求解释、领域审核、风险定级、基线整改和最终复核。
- 本轮仅为文档审核和小范围基线修订，按路由规则由主代理直接完成。
- 后续进入模型、迁移、服务和并发测试实现时，必须把明确文件范围和验证标准交给 `luna-worker`；主代理只做协调和复核，不重复编码。

## 2. 审核结论摘要

经整改，以下业务决策可以作为后续领域契约输入：

1. 现有协同系统架构和权限体系继续作为唯一技术及授权底座。
2. 订单创建时运输路线未决，生产完成后由采购确定散货或柜货。
3. 一个订单允许部分装箱、多个装箱批次和多次发货。
4. 散货由采购按区域将不同供应商已完成批次归集至受控集货地点，再与系统外其他公司货物拼柜、报关、统一发货。
5. 其他公司货物明细不进入系统，只保存与本企业货物履约有关的外部引用。
6. 小程序继续使用原生架构和现有认证/权限合同，并设置 Android、iPhone 双真机发布门禁。

## 3. P1 发现与整改结果

### SCM-REQ-V2-R1-P1-001 数量权威源与守恒公式缺失

- 风险：多个批次并发时可能超生产数量装箱，或订单累计量被客户端/缓存覆盖。
- 整改：明确采购订单明细单位是数量权威单位；冻结生产、装箱、发货、到仓、清货守恒不等式，并规定台账为权威源。
- 状态：`CLOSED`

### SCM-REQ-V2-R1-P1-002 已封箱后的多发运分配单位不唯一

- 风险：以“箱或数量”任选会使一个实体箱在两个发运单中被重复消费。
- 整改：冻结已封箱后以完整箱为最小物理分配单位；拆箱必须产生受控重新装箱版本和审计事件。
- 状态：`CLOSED`

### SCM-REQ-V2-R1-P1-003 动作责任主体与证据边界不完整

- 风险：采购、供应商、物流、报关和仓库可能越权替代对方推进状态。
- 整改：按动作冻结责任主体，并要求每个状态动作在后续契约中声明前态、权限、证据、幂等结果和撤销方式。
- 状态：`CLOSED`

### SCM-REQ-V2-R1-P1-004 现有单批次约束缺少可审计迁移路径

- 风险：直接删除 `active_guard` 唯一约束会造成历史数据重复消费或迁移不可回滚。
- 整改：新增只读盘点、异常隔离、台账回填、双读校验、服务切换和旧约束退役的分波迁移原则。
- 状态：`CLOSED`

### SCM-REQ-V2-R1-P1-005 小程序构建版本不可重复

- 风险：`libVersion: trial` 会让同一提交在不同日期产生不同运行结果，真机证据不可追溯。
- 整改：禁止漂移版本；每个候选构建必须产生含工具、基础库、客户端、系统、机型、域名摘要和 Git 提交的版本清单。执行时只能依据微信官方资料及开发者工具冻结版本；本次尝试访问官方资料未取得可用页面，因此未臆造具体版本号。
- 状态：`CLOSED_AT_BASELINE`；具体版本值是 `SC-MINIAPP-COMPAT-1` 的进入门禁。

## 4. P2 处理决定

### SCM-REQ-V2-R1-P2-001 区域自动归类规则

- 决定：首期不做系统自动决定。系统可按供应商/地址给出建议，最终集货地点必须由采购确认并记录建议值与最终值。
- 状态：`ACCEPTED_FOR_MVP`

### SCM-REQ-V2-R1-P2-002 外部货代/报关数据集成

- 决定：首期只支持受控人工录入或文件引用，不在本阶段连接货代、报关或第三方账号；未来集成另行审核凭据、重试、对账和幂等合同。
- 状态：`DEFERRED_WITH_BOUNDARY`

### SCM-REQ-V2-R1-P2-003 履约摘要物化

- 决定：台账是权威源；订单摘要可物化以提升查询性能，但必须提供重建和差异检测命令，差异不得静默修正。
- 状态：`ACCEPTED_WITH_GUARDRAIL`

### SCM-REQ-V2-R1-P2-004 两周业务指标样本

- 决定：本机开发阶段采用合成数据验证守恒、并发和权限，不伪造业务成效；试点指标、样本量和停止条件在获得受控试点授权后单独冻结。
- 状态：`DEFERRED_UNTIL_PILOT_AUTHORIZATION`

## 5. 进入下一阶段的强制条件

下一阶段为 `SC-F2-MULTI-0 多批次/多发运领域契约冻结`，必须交付：

- 订单明细履约台账事件和守恒公式；
- 批次、箱、集货和发运聚合之间的身份与唯一约束；
- 所有动作状态机、权限、DataScope、证据、幂等和撤销矩阵；
- MySQL 加锁顺序、唯一约束、死锁重试和 ORM 绕过测试清单；
- 现有 `active_guard` 的迁移前盘点、回填、双读、切换、退役及回滚合同；
- 明确 Web、供应商小程序和内部小程序各自可见及可写字段。

在上述契约通过独立审核前，不得委派模型/迁移/服务编码。

## 6. 审核结论

`SCM-REQ-V2-R1` 的五项 P1 已在本地基线层关闭，两项基线可作为下一阶段输入。当前批准的是 L2 级本机变更集准备，不包含线上写入、生产迁移、正式发布或第三方账号连接授权。
