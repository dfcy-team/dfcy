## 4. 业务合同融合规则

### 4.1 订单、装箱和发货

- 保留源需求采购订单、发货单、货柜和装箱审核状态的业务含义。
- 当前代码状态与源需求状态不一致时，必须建立显式映射或迁移方案，标记为“需重构”，不得由客户端直接覆盖状态。
- 同一订单支持部分装箱、多个装箱批次、多个发货单和多订单合并发货。
- 源需求的 `single_packing_batch_per_order` 作为可配置业务规则实现；关闭时允许多个未结束批次。数据库数量守恒和同箱防重始终生效。
- 订单级累计状态由明细履约台账和各发货单汇总派生，禁止多张单据最后写入覆盖。

### 4.2 散货、集货与柜货

- 源需求的散货发货、货运单、出货审核和柜货装柜流程全部保留。
- 已实现的区域集货、集货地点、供应商交接、统一拼柜、报关、到港、到仓和清货能力作为安全增强子流程保留。
- 直接散货发运与区域集货发运必须使用明确的路线/模式字段和独立前置条件；最终状态映射在领域契约审核中冻结。
- 一个完整物理箱同时最多只能有一个有效集货或发运消费；集货转发运使用原子消费权转移。
- 外部其他公司货物只保存必要拼柜引用，不导入其订单、供应商或箱明细。

### 4.3 附件、标签和审核

- 4 类必传照片、条件必传抽检视频、货运单、装柜/封条照片和审核结论全部进入受控附件体系。
- 客户端不得提交任意存储 URL、扫描通过状态、租户或业务绑定；这些字段由服务端派生。
- 外箱标签必须使用准入中文字体、受控 renderer 和可重放输入快照。
- 已接受附件和已完成批次不得原地篡改；更正、驳回、替代和删除产生审计事件。

### 4.4 费用、报表、通知和设置

- 费用计算必须保留币种、汇率来源、分摊口径、舍入规则和重算版本。
- 报表数字必须可追溯到权威业务数据；供应商评级公式、时间窗、缺失值和导出权限单独冻结。
- 微信/飞书通知使用现有受控集成，不在客户端保存密钥；通知发送必须服从用户开关和审计策略。
- 系统设置按租户保存，敏感开关要求专用权限、版本检查和变更审计。

## 5. 数据、安全和并发底线

以下已审核能力属于 V3 的不可弱化约束：

- 所有业务对象带租户或供应商归属，查询与动作均防跨租户、防枚举。
- 数量满足生产、预留、完成装箱、发货、到仓、清货守恒。
- 写动作使用事务、确定性锁顺序、数据库约束、`expected_version` 和 `Idempotency-Key`。
- MySQL 1205/1213 等可重试冲突不得形成部分写入。
- 不可变事件和动作账本只追加，不允许 ORM、批量更新或后台任务绕过领域服务。
- 正式线上供应链系统保持隔离；生产迁移、数据导入、部署和账号激活必须另行立项审批。

- 必须覆盖微信支持的 Android 与 iPhone 真机，不以开发者工具代替真机结论。

- 每个关键流程保存设备、系统、微信版本、时间、构建版本、截图/录像和结果。

## 7. 状态定义

追踪矩阵统一使用：

- `已实现`：本地代码、迁移、权限、测试和客户端入口均有证据。
- `部分实现`：仅领域/API/单一客户端或受控开发能力完成。
- `未实现`：当前仓库没有满足需求的业务能力。
- `需重构`：已有实现与最新需求状态、流程或数据合同冲突。
- `待确认`：源文件内部或与既有明确决策存在歧义，编码前需独立合同冻结。

“历史阶段审核通过”不等于“V3 完整需求完成”。
