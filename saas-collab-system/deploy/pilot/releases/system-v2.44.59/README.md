# V2.44.59 生产候选发布包

本目录是基于当前 VM `v2.44.58-deployed` 的候选材料。审查基线为
`7fd5f7f35630a10a5b88da9ae228deb9c31aee08`；该 SHA 只表示本批次要求的
父链起点，不代表已经完成现场接管。仓库没有可直接冒充 V2.44.58 的旧发布
脚本或镜像摘要，因此本包不会猜测父镜像，也不会复用 V2.44.52 的逻辑。

## 生产闭环

```
CI main ancestry + build/push + migration digest
              |
              v
  build-v24459.sh -> candidate JSON (no credentials)
              |
              v
  architect/owner verifies current.json + plan + backup gates
              |
              v
  register-v24459.sh --apply -> atomic approved-candidate.json
              |
              v
  preflight-v24459.sh -> baseline, permissions, SSH port, TLS/token files
              |
              v
  migrate-v24459.sh (architect approval) -> production-deploy's guarded migrate
              |
              v
  deploy-v24459.sh --apply -> generic runner -> production-control deploy
              |
              v
  post-verify-v24459.sh -> current ledger + health + runtime baseline
```

`rollback-v24459.sh --apply` is the emergency path. It uses the same approved
candidate only when its release SHA is the running `current.json.release_sha`
and its parent SHA is `previous.json.release_sha`; reason/actor/registry token
are never taken from an API request or command-line argument. Existing
`production-control` retains flock, immutable digest/OCI revision checks,
pre-migration backup, health verification, automatic rollback and JSONL audit.

## Required staging

1. On a protected CI runner, check out the exact candidate commit on `main`.
   Build and push backend/frontend images with OCI revision equal to that full
   SHA; record immutable digests and calculate the migration-tree SHA. The
   production VM must never build source or receive a long-lived registry token.
2. Run `build-v24459.sh` with `CI=true` (or `GITHUB_ACTIONS=true`) and these
   non-secret CI outputs: `PILOT_RELEASE_SHA`,
   `PILOT_PARENT_RELEASE_SHA=7fd5f7f35630a10a5b88da9ae228deb9c31aee08`,
   `PILOT_BACKEND_IMAGE`, `PILOT_FRONTEND_IMAGE`, `PILOT_REDIS_IMAGE`,
   `PILOT_MIGRATION_SHA256`, `PILOT_RELEASE_ACTOR`, `PILOT_REGISTRY_USER`,
   `PILOT_CANDIDATE_OUTPUT`, and the three `*_ATTESTED=true` flags. The output
   is a non-secret candidate manifest; the template `manifest.json` is not an
   approved candidate and must not be staged as-is.
3. On the VM, first confirm the live `current.json.release_sha` is the parent
   SHA recorded in the generated candidate. Then run
   `register-v24459.sh --source=/absolute/ci-candidate.json --apply`. The
   installed `stage-approved-candidate.sh` validates the release plan, image
   repositories/digests, CI attestations and parent ledger, writes mode `0440`
   `root:saas-runner` and replaces the target atomically. It does not accept or
   read a registry credential.
4. Provision the registry token separately at
   `/etc/saas-collab/runner/registry-token` (`root:root`, `0400` or
   `0600`; it is consumed only by the root bridge) and provision the runner
   TLS/token files as described in
   `deploy/pilot/runner/README.md`. Never put any of them in Git, this package,
   a Dockerfile, Compose interpolation, or an audit/evidence record.

## Preflight and known field conditions

Run as root from the installed release checkout:

```sh
bash deploy/pilot/releases/system-v2.44.59/preflight-v24459.sh
```

The runner preflight is read-only and defaults to checking the controlled
external SSH endpoint `192.168.2.10:22131`. The application VM's internal
endpoint is `192.168.174.131:22`; set `PILOT_VM_HOST` and `PILOT_VM_SSH_PORT`
for the owner-approved route rather than changing the script. The public
application hostname is `xtsy.dingfengchuangyu.com`. TCP reachability is not
authorization and the preflight never opens a shell or changes the VM.

The current known blocker is ownership, not a guessed SSH outage: the
production-control tree/baseline/live environment/backup hook must be
root-owned and non-writable by `dfcy01` or `saas-runner`; live env must have
`PRODUCTION_REQUIRE_BACKUP=true` and a root-owned, non-symlink absolute
executable `PRODUCTION_BACKUP_COMMAND`. `production-baseline-check --runtime`
and runner preflight intentionally fail until those facts are repaired and the
baseline is regenerated by an architect. `PRODUCTION_DEPLOY_USER` (default
`dfcy01`) must also be absent from the Docker group; the runtime check fails
closed when that broad root-equivalent membership remains. This package does not change users,
groups, permissions, firewall rules, SSH keys, or services.

## Migration, deploy and rollback

`migrate-v24459.sh` is an architecture approval gate; it deliberately does not
run a standalone migration. With `PILOT_ARCHITECT_MIGRATION_APPROVED=true`,
the ordinary `production-deploy` fixed control path performs the configured
backup, migration service, health checks and automatic rollback under its lock.
Run:

```sh
bash deploy/pilot/releases/system-v2.44.59/migrate-v24459.sh
bash deploy/pilot/releases/system-v2.44.59/deploy-v24459.sh --apply
bash deploy/pilot/releases/system-v2.44.59/post-verify-v24459.sh
```

If deployment health fails, let production-control complete its automatic
rollback first. For an approved emergency rollback:

```sh
bash deploy/pilot/releases/system-v2.44.59/rollback-v24459.sh --apply
bash deploy/pilot/releases/system-v2.44.59/post-verify-v24459.sh
```

Database rollback is not inferred or run automatically. An irreversible
migration requires the architect's backup-restore or forward-fix procedure;
the `recovery` runner operation only reconciles the registered application
services and reports `actual_rpo_minutes=0`/measured
`actual_rto_minutes` with scope `application_service_reconciliation`.

## Compose and secrets

`deploy/production-control/production-compose.yml` and
`deploy/pilot/application/docker-compose.pilot-app.yml` mount OpenAI key and
runner token/CA only as read-only files into backend/celery. `celery-beat` does
not receive these secrets. The backend prefers `OPENAI_API_KEY_FILE`; examples
contain only paths/placeholders. The runner is a separate host systemd service,
has no Docker socket or Docker group, and is reached over private TLS using a
certificate whose SAN matches the configured allowlisted hostname.

No release command has been run against the VM as part of preparing this
candidate package.
